# External inbox monitoring — inactive preparation

## Implemented boundary

`monitor.mjs` is a dependency-free Node one-shot check for an external monitoring
runner. It requires an explicit `--check`; otherwise it reports UNKNOWN and makes
no request. Importing the module has no network side effect. It reads the HTTPS
origin from INBOX_MONITOR_ORIGIN and its dedicated token from INBOX_MONITOR_TOKEN.
There is no real origin, token, provider, schedule or destination in the repo.
`monitor-plan.example.json` is an **inactive proposal**, not a runnable scheduler
or installed provider configuration. No alerts have been sent.

Worker binding MONITOR_SECRET is optional and must be distinct from both signing
and consumer secrets (32–256 URL-safe characters). Absent binding disables the
monitor route; malformed or reused configured credentials fail all request routes
closed. This prevents a nominal monitor token from acquiring consumer privileges.
POST `/monitor/status` accepts only `{}` and that monitor credential. It executes
only aggregate SELECT: no claims, ACK, maintenance, requeue, payload or ID access.
The consumer credential is not accepted at this route; the monitor credential is
not accepted at any consumer route. No schema migration is needed for this slice.

The probe uses ordinary verified TLS/hostname checking, no redirect following,
a five-second total response deadline and an 8192-byte cap. Test-only CA/deadline
injection is unavailable through its CLI. Output contains fixed reason codes and
validated aggregate numbers, never arbitrary response data, endpoint URLs,
credentials or exception details. Non-200 responses, network failures, oversized
or malformed data, inconsistent counts/attention, and observations older than
120 seconds or >30 seconds in the future return UNKNOWN (exit 3).

## Signal contract

| Exit | Result | Conditions |
| --- | --- | --- |
| 0 | OK | Valid fresh status with no attention condition |
| 1 | WARNING | >=80% rows or body-byte budget, or oldest unprocessed >=1 hour |
| 2 | CRITICAL | >=95% budget, any quarantine/exhausted event, or age >=24 hours |
| 3 | UNKNOWN | No trustworthy fresh result, bad configuration, or inactive check |

Status timestamps are generated by the database clock. The response is no-store.
This checks Worker/DB reachability and current inbox pressure, **not** successful
Tebex delivery, consumer liveness while the inbox is empty, a working maintenance
Cron, actual chat/Discord receipt, or backup recoverability. No synthetic payment
or notification is sent. A recent timestamp is not a heartbeat from the plugin.
The observer must detect its own missed runs from outside the probe process.

## External integration proposal and response

Before activation, assign primary/backup owners and an approved destination,
choose an independently hosted runner outside Bloom and Cloudflare, and provision
a least-privilege monitor credential separately. The example proposes five-minute
checks, a ten-second supervisor kill deadline and an independent dead-man incident
if no result arrives within 15 minutes. Treat CRITICAL/UNKNOWN as incidents after
two consecutive results and WARNING after three. Recover after three OK results;
deduplicate by inbox plus incident type, repeat at most hourly, and keep a separate
record of acknowledgement/owner. Pure routing decisions are now locally tested in
[alert-routing.mjs](alert-routing.mjs); see [routing contract](alert-routing.md).
Durable persistence, delivery and independent watchdog scheduling must still be
implemented and tested in the chosen provider; the one-shot probe does not
implement them. Do not make GitHub CI or a Cloudflare Cron the only observer.

- UNKNOWN: check observer health/time/DNS/TLS, credential configuration and
  provider status. Never treat an error or absent check as OK.
- Capacity/backlog: inspect official sync/eligibility and consumer availability,
  quota/latency and expected payment volume. Do not auto-raise limits or delete
  pending work to make the alert green.
- Quarantine: follow the metadata inspection and explicit recovery procedure in
  [policy.md](policy.md). Do not bulk replay or dispatch directly from the inbox.
- Recovery: verify inbox state and existing outbox, record the actual fix and
  continue observation. A cleared aggregate does not prove a customer saw a message.

Keep 14 days of sanitized check results as a proposed operational default, pending
owner approval. Disable request-header/body tracing in the chosen provider, keep
tokens in its secret store, and exclude secrets from command-line arguments and
CI artifacts. No sensitive monitor result is currently stored by the one-shot
adapter. External storage/access/deletion behavior must be verified before use.

## Query cost and acceptance

Status now uses transactional global and source counters with indexed age and
exhaustion-presence queries. `exhausted_present` is 0 or 1, never an exact count;
the separately invoked operator count can still scan the bounded pending set.
The monitor requires the v5 field and rejects older or malformed responses. See the measured
[quota review](quota-review.md); do not assume a shared account budget is met.
Physical storage and Time Travel remain separate from the reported payload bytes.

Acceptance requires isolated hosted DNS/TLS and credential rotation/revocation
checks, simulated outage/pressure/quarantine, missing-run detection, dedup/recovery
and delivery to the approved alert destination, plus documented ownership and
query-cost measurements. Those actions require separate authorization. No
monitor, provider subscription, notification channel or Cron was activated.

## Verification

Before implementation the classification test failed against an UNKNOWN stub and
the local D1 route test failed with 404; the malformed-status test already passed
against that stub and is not claimed as red evidence. Local tests now exercise
credential isolation, collision failure, no mutation on monitoring, fresh/stale
classification, safe output, inactivity and a real temporary HTTPS fixture with
trust/hostname/redirect/size/deadline failures. CI repeats the local tests; it does
not execute the probe against a live inbox. See draft PR #9 for exact-head results.

CI log review also found deprecated Python sequence bindings for numbered SQL
parameters in the local SQLite harness. Both harnesses now bind numeric keys
explicitly, and CI treats DeprecationWarning as an error. This was an observed
compatibility warning, not a claimed production failure.

Account-specific plan, sampled backup window and destination findings are recorded
in [account validation](account-validation.md). No hosted acceptance is claimed.
